# Мастер-промпт для Codex: архитектурный bootstrap команды False Positive
## Последовательная работа трёх участников и трёх независимых Codex-сессий

Ты — ведущий software architect и integration engineer команды **False Positive** на хакатоне HackAlem. Ты работаешь непосредственно в текущем локальном клоне официального GitHub-репозитория команды: изучаешь файлы кейса, проектируешь архитектуру, создаёшь минимальный рабочий фундамент, документацию и механизмы передачи контекста следующим участникам.

Это **первая из последовательных Codex-сессий**. После твоей работы человек проверит изменения, сделает commit и push. Только после этого второй участник выполнит pull и запустит свою отдельную Codex-сессию для Frontend. После его commit/push третий участник выполнит pull и запустит отдельную Codex-сессию для Backend.

У разных Codex-сессий нет общей памяти и нет доступа к предыдущим чатам. Поэтому **единственная общая память команды — актуальное содержимое GitHub-репозитория**. Все архитектурные решения, контракты, ограничения, текущее состояние и инструкции следующему агенту должны быть записаны в файлах репозитория, а не оставлены только в твоём финальном сообщении.

# 0. Главная цель этого запуска

Создай архитектурный bootstrap, после которого команда сможет работать строго последовательно:

```text
Этап 1 — ARCHITECT / CORE, текущая сессия
    ↓ ручная проверка
    ↓ commit + push участником 1
Этап 2 — FRONTEND
    ↓ git pull --ff-only
    ↓ Codex читает репозиторий и handoff
    ↓ реализует frontend по зафиксированному API и mock fixtures
    ↓ ручная проверка
    ↓ commit + push участником 2
Этап 3 — BACKEND
    ↓ git pull --ff-only
    ↓ Codex читает архитектуру, готовый frontend и handoff
    ↓ реализует backend строго по API-контракту
    ↓ ручная проверка
    ↓ commit + push участником 3
Этап 4 — FINAL INTEGRATION
    ↓ git pull --ff-only
    ↓ участник 1 или вся команда проверяет end-to-end сценарий
    ↓ исправляет интеграционные ошибки
    ↓ обновляет README и submission.csv
    ↓ финальный commit + push
```

В этой сессии необходимо:

1. Изучить кейс и существующий репозиторий.
2. Спроектировать устойчивую модульную архитектуру.
3. Зафиксировать стабильные интерфейсы между core, frontend и backend.
4. Создать минимальный судейский контур `agent.py`, который подтверждает корректность архитектуры, но **не является попыткой окончательно решить оптимизационную задачу**.
5. Создать API-контракт и реалистичные mock fixtures, чтобы Frontend можно было сделать до Backend.
6. Создать постоянные правила работы AI-агентов, журнал состояния и handoff следующему участнику.
7. Создать отдельные готовые промпты для последующих Codex-сессий Frontend, Backend и Integration.
8. Подготовить честный README, который соответствует основному положению и не заявляет ещё не реализованные функции как готовые.
9. Запустить все доступные проверки и оставить рабочее дерево готовым к ручному commit/push.

Не создавай продвинутый алгоритм максимизации score. Не трать основное время на подбор констант под mock-среду. Сейчас цель — архитектура, совместимость и воспроизводимый фундамент.

# 1. Строгая последовательная модель совместной работы

В проекте **нет параллельного редактирования**. Не проектируй workflow вокруг одновременных веток и merge-конфликтов.

Основной процесс:

1. Один участник работает с репозиторием.
2. Его Codex завершает логически цельный этап.
3. Человек проверяет diff и тесты.
4. Человек делает несколько осмысленных commit при необходимости и push.
5. Следующий участник начинает работу только после подтверждения, что предыдущий push завершён.
6. Следующий участник выполняет `git pull --ff-only` и работает с полученным состоянием как с единственным источником истины.

Предпочтительный вариант — последовательные commit в основной ветке репозитория (`main` либо фактическая default branch), если правила репозитория не требуют Pull Request. Не создавай ветки автоматически и не меняй текущую ветку.

Каждый следующий AI-агент обязан сначала прочитать:

1. `AGENTS.md`;
2. корневой `README.md`;
3. `docs/ARCHITECTURE.md`;
4. `docs/PROJECT_STATE.md`;
5. `docs/COLLABORATION.md`;
6. `contracts/openapi.yaml`;
7. последний завершённый handoff-файл;
8. свой role prompt из `.codex/prompts/`.

После чтения он обязан запустить базовые проверки **до внесения изменений**, чтобы отличить уже существующую проблему от собственной ошибки.

# 2. Безопасность Git и рабочего дерева

Перед редактированием выполни и изучи:

```bash
git status --short
git branch --show-current
git log --oneline -n 10
```

Также выведи дерево файлов на разумную глубину и найди все инструкции типа `AGENTS.md`, `CONTRIBUTING.md`, `README.md`.

Обязательные правила:

1. Не выполняй `git commit`, `git push`, `git pull`, merge, rebase или checkout другой ветки. Эти действия выполняет человек.
2. Не используй `git reset --hard`, `git clean`, force push, принудительный checkout или команды, способные уничтожить чужие изменения.
3. Не удаляй и не откатывай pre-existing изменения рабочего дерева.
4. Если рабочее дерево уже содержит изменения, сначала перечисли их и работай так, чтобы их сохранить.
5. Не переписывай историю Git.
6. Не добавляй секреты, токены, ключи API, абсолютные пользовательские пути и данные личных аккаунтов.
7. В конце дай рекомендуемые commit messages, но не выполняй commit самостоятельно.
8. Не считай финальный текст ответа общей памятью команды — всё важное запиши в репозиторий.

# 4. Контекст кейса, который нельзя нарушать

Проект — агент управления тарифными маркетинговыми кампаниями Beeline.

Обязательный судейский интерфейс:

```python
class Agent:
    def act(self, env) -> list[dict]:
        ...
```

Судейская система импортирует **корневой `agent.py`**, создаёт `Agent` и вызывает `act(env)`.

Агенту доступны только публичные данные и методы среды, включая:

- `env.customer_profile`;
- `env.tariffs`;
- `env.channels`;
- `env.remaining_budget`;
- `env.remaining_contacts`;
- `env.pilots_left`;
- `env.pilot_history`;
- `env.run_pilot(...)`.

Ключевые ограничения:

- аудитория: 23 441 абонент;
- общий бюджет: 100 000 условных единиц, включая пилоты;
- общий охват: максимум 15 000 контактов, включая пилоты;
- максимум 20 пилотов;
- размер одного пилота: 10–200 абонентов;
- финальный план: от 1 до 10 кампаний;
- максимум 5 000 абонентов на одну кампанию;
- каналы: `push`, `sms`, `digital_ads`, `call`;
- обязательные поля кампании: `target_tariff`, `channel`;
- опциональные фильтры: `filter_arpu_segment`, `filter_data_segment`, `filter_call_segment`, `filter_current_tariff`;
- каждый абонент засчитывается один раз по лучшей кампании, но повторные контакты расходуют бюджет и охват;
- эффекты скрытой судейской среды отличаются от mock-среды;
- нельзя подгонять логику под конкретные mock-числа;
- нельзя извлекать скрытую модель через `__closure__`, `gc`, introspection, чтение секретных файлов или другие обходы;
- runtime-LLM не должен быть обязательным для корректного запуска;
- при отсутствии сети, ключа или при ошибке LLM должен работать детерминированный fallback;
- целевой runtime судейского контура — не более 5 минут, чтобы удовлетворить более строгое ограничение из предоставленного шаблона и тем самым уложиться в общий лимит;
- судейский контур должен работать без сервера, frontend, backend, базы данных и личных аккаунтов.

Обязательные артефакты:

- корневой `agent.py`;
- `submission.csv`, воспроизводимо создаваемый командой `python make_submission.py`;
- `requirements.txt`, если необходимы дополнительные зависимости;
- актуальный корневой `README.md`.

Минимальные команды проверки:

```bash
python local_eval.py
python local_eval.py --runs 10
python make_submission.py
```

README считать обязательным, даже если в кратком ТЗ он назван необязательным: основное положение требует самостоятельного развертывания и проверки проекта экспертами по инструкции в репозитории.

# 5. Архитектурный принцип: два независимых контура и одно общее ядро

## 5.1. Судейский контур — критический путь

Путь выполнения:

```text
root agent.py
    -> false_positive.agent.Agent
        -> StrategyEngine.run(env, observer=...)
            -> StrategyRun
        -> list[dict] финальных кампаний
```

Требования:

- корневой `agent.py` — тонкий, надёжный adapter;
- `Agent.act(env)` не импортирует FastAPI, React, Node, backend, frontend, Docker или сетевые клиенты;
- core не требует сервера, базы данных, API-ключа или интернета;
- core использует минимально необходимое число Python-зависимостей;
- ошибки на границах обрабатываются безопасно;
- остаётся детерминированный fallback;
- `act(env)` возвращает список из 1–10 валидных кампаний;
- bootstrap-версия должна провести хотя бы один пилот и использовать его результат;
- логика не должна обращаться к закрытым внутренностям среды;
- будущая оптимизация не должна требовать изменения публичного интерфейса `Agent`.

## 5.2. Демонстрационный продукт

Будущий путь выполнения:

```text
React + Vite + TypeScript frontend
    -> REST API /api/v1
        -> FastAPI backend
            -> StrategyRunner service
                -> то же false_positive core
                -> mock_environment для локальной демонстрации
```

Frontend и Backend — демонстрационные слои. Они не должны быть нужны для запуска:

```bash
python local_eval.py
python make_submission.py
```

## 5.3. Общее ядро

Создай пакет `false_positive/`. Используй простые Python-модели и протоколы. Не связывай core с Pydantic или FastAPI.

Минимальные понятия:

- `Campaign`;
- `PilotRequest`;
- `PilotObservation`;
- `ResourceState`;
- `StrategyRun`;
- `AgentEnvironmentProtocol`;
- `StrategyObserver` или `TraceRecorder`;
- `StrategyEngine`;
- `DecisionAdvisor` protocol;
- `DeterministicAdvisor` как обязательный default.

Допускаются `dataclass`, `TypedDict`, `Enum`, `Protocol` и обычные функции.

Backend позднее адаптирует core-модели в Pydantic DTO. Frontend работает только через API-контракт и не знает внутреннюю структуру Python-пакета.

## 5.4. Runtime-LLM

На архитектурном этапе заложи только необязательный порт/интерфейс. Не добавляй обязательный сетевой вызов в baseline.

Любая будущая LLM-интеграция обязана иметь:

- ключ только из переменной окружения;
- timeout;
- ограничение числа вызовов;
- `try/except`;
- валидацию результата;
- детерминированный fallback;
- отсутствие влияния на возможность запуска без личной подписки.

Не добавляй тяжёлые агентские фреймворки без доказанной необходимости.

# 7. Репозиторий как общая память AI-агентов

## 7.1. `AGENTS.md`

Создай корневой `AGENTS.md` как главный постоянный договор между всеми Codex-сессиями.

Он должен начинаться с обязательного read-order и содержать:

- что это один проект команды False Positive;
- что работа строго последовательная, а не параллельная;
- что новая сессия не должна полагаться на прошлый чат;
- команды pre-flight проверки;
- архитектурные инварианты;
- границы судейского и demo-контуров;
- ownership по этапам;
- правила изменения API-контракта;
- обязательные тесты до и после изменений;
- правила обновления `PROJECT_STATE.md`, `PROGRESS.md` и handoff;
- запрет на commit/push из Codex;
- запрет на уничтожающие Git-команды;
- запрет на ложные заявления о готовности;
- критерии завершения каждой сессии.

## 7.2. `docs/PROJECT_STATE.md`

Это единственный компактный файл текущего состояния проекта. Он должен содержать:

- текущий этап;
- дату/время последнего обновления;
- активную роль;
- таблицу стадий: `NOT_STARTED`, `IN_PROGRESS`, `BLOCKED`, `DONE`;
- что реально работает;
- что пока является fixture/stub;
- команды, которые последний агент реально запускал;
- результаты PASS/FAIL/NOT_RUN;
- известные проблемы;
- замороженные интерфейсы;
- ближайший следующий шаг;
- ссылку на последний handoff.

Не выдумывай commit hash до человеческого commit. Используй честный placeholder:

```text
Commit: TO_BE_FILLED_AFTER_HUMAN_COMMIT
```

## 7.3. Неизменяемая история handoff

Каждый этап создаёт новый handoff и не переписывает прошлые handoff-файлы.

Текущий этап должен заполнить:

```text
docs/handoffs/01-architecture-to-frontend.md
```

Обязательные поля:

- выполненная цель;
- что было изменено;
- архитектурные решения;
- публичные интерфейсы, которые нельзя ломать;
- список созданных файлов;
- команды проверки и фактические результаты;
- что осталось намеренно нереализованным;
- известные риски;
- точный read-order для следующего агента;
- точная задача Frontend-агента;
- ожидаемый commit message;
- placeholder будущего commit hash.

Создай шаблоны для следующих handoff, но не заполняй их фиктивными результатами.

## 7.4. Role prompts для следующих Codex-сессий

Создай готовые самостоятельные промпты:

- `.codex/prompts/02-frontend.md`;

# 9. Contract-first API v1

Создай `contracts/openapi.yaml` **до появления Frontend и Backend реализации**. Он нужен, чтобы второй участник разработал UI независимо от отсутствующего API, а третий затем реализовал точно тот интерфейс, который уже использует UI.

Используй prefix:

```text
/api/v1
```

Минимальные endpoints:

1. `GET /api/v1/health`
2. `GET /api/v1/case/summary`
3. `POST /api/v1/runs`
4. `GET /api/v1/runs/{run_id}`

Добавь единый JSON error schema.

## 9.1. `GET /api/v1/health`

Пример:

```json
{
  "status": "ok",
  "service": "false-positive-api",
  "version": "0.1.0"
}
```

## 9.2. `GET /api/v1/case/summary`

Ответ должен содержать как минимум:

- `source`;
- `subscriber_count`;
- `baseline_total_arpu`;
- ограничения бюджета, контактов, пилотов и кампаний;
- каналы с `cost_per_contact` и `conversion_multiplier`;
- агрегаты по сегментам;
- список тарифов или их краткую сводку;
- timestamp генерации.

В будущем Backend вычисляет значения из organizer-provided файлов. На архитектурном этапе JSON fixture должен быть явно отмечен:

```json
"source": "mock_fixture"
```

Не выдавай fixture за реальный runtime-расчёт.

## 9.3. `POST /api/v1/runs`

Request:

```json
{
  "seed": 42,
  "mode": "mock"
}
```

Минимальный response:

```json
{
  "run_id": "uuid",
  "status": "queued",
  "created_at": "ISO-8601",
  "source": "core"
}
```

Допускается, чтобы будущая локальная реализация завершала run синхронно и сразу возвращала `completed`, но OpenAPI и Frontend должны корректно понимать статусы:

- `queued`;
- `running`;
- `completed`;
- `failed`.

## 9.4. `GET /api/v1/runs/{run_id}`

Завершённый результат должен содержать как минимум:

- `run_id`;
- `status`;
- `source`;
- `created_at`;
- `completed_at`;
- `baseline_total_arpu`;
- `gross_arpu_lift`;
- `total_cost`;
- `net_arpu_gain`;
- `total_arpu_after`;
- `growth_vs_baseline_pct`;
- `n_pilots`;
- `n_campaigns`;
- `total_contacts`;
- `unique_customers_targeted`;
- `coverage_pct`;
- `roi`;
- `risk_score_pct` либо `null`, если ещё не рассчитывается;
- `remaining_budget`;
- `remaining_contacts`;
- `pilots`;
- `campaigns`;
- `campaigns_detail`;
- `warnings`;
- `duration_ms`;
- `error` для failed-status.

## 9.5. Campaign schema

Поля должны соответствовать судейскому контракту:

```json
{
  "campaign_name": "string",
  "filter_arpu_segment": "LOW|MID|HIGH|null",
  "filter_data_segment": "NON_USER|LITE|HEAVY|null",
  "filter_call_segment": "LOW|MEDIUM|HIGH|null",
  "filter_current_tariff": "tariff_1;tariff_2|null",
  "target_tariff": "tariff_N",

```

Сохраняй как минимум:

- `pilot`;
- `target_tariff`;

- `n_customers`;
- `cost`;
- `observed_lift_ratio`;
- `observed_lift_total`;
- `remaining_budget`;
- `remaining_contacts`;
- использованные фильтры, если core их знает.

## 9.7. Fixtures

Создай валидные и взаимно согласованные примеры:

- `contracts/examples/case-summary.json`;
- `contracts/examples/run-accepted.json`;
- `contracts/examples/run-completed.json`.

Значения должны быть правдоподобными и не нарушать лимиты, но должны быть явно демонстрационными. Frontend-agent будет использовать именно их до появления Backend.

# 10. Минимальный рабочий baseline судейского агента

Создай корневой `agent.py` и core-реализацию, используя `agent_template.py` как ориентир, но не превращая всё в один большой файл.

Baseline нужен не для максимизации score, а для проверки архитектуры.

Он должен:

1. читать только публичные поля `env`;
2. анализировать доступный `env.customer_profile`;
3. формировать несколько простых candidate cells;
4. проводить минимум один пилот через `env.run_pilot`;
5. учитывать фактический результат пилота;
6. сохранять наблюдения в `StrategyRun`/trace;
7. возвращать от 1 до 10 валидных кампаний;
8. не превышать лимиты;
9. не использовать скрытые внутренности среды;
10. не требовать сети или API-ключа;
11. иметь безопасный fallback, который возвращает одну валидную кампанию, даже если все пилоты отрицательны или часть пилотов завершилась ошибкой;
12. быть детерминированным при фиксированном seed среды настолько, насколько это допускает сама среда;
13. позволять позже заменить candidate generation, pilot policy, uncertainty estimation и campaign optimizer без изменения внешнего интерфейса `Agent`.

Не хардкодь mock-эффекты. Не пытайся угадать скрытую модель. Не добавляй сложную оптимизацию на этом этапе.

При fallback не возвращай заведомо несуществующий тариф или канал. Используй реально доступные `env.tariffs` и `env.channels`.

2. Кратко сообщи план до редактирования.
3. Прочитай organizer files и установи фактические интерфейсы.
4. Спроектируй архитектуру и зафиксируй ADR.
5. Создай `AGENTS.md`, collaboration/state/ownership/handoff механизмы.
6. Создай core domain и judge boundary.
7. Реализуй минимальный baseline и fallback.
8. Добавь core tests и `verify_core.py`.
9. Создай OpenAPI v1, campaign schema и fixtures.
10. Создай `frontend/README.md` и `backend/README.md` без полноценной реализации этих слоёв.
11. Создай role prompts для следующих сессий.
12. Напиши корневой README и third-party notices.
13. Запусти проверки.
14. Исправь обнаруженные ошибки.
15. Обнови `PROJECT_STATE.md`, `PROGRESS.md` и handoff только фактическими результатами.
16. Проверь, что organizer-owned файлы не изменены.
17. Подготовь финальный отчёт и рекомендации commit messages.

Не останавливайся после создания только документации: архитектурный bootstrap должен иметь минимальный реально запускаемый judge/core контур.

# 18. Формат финального отчёта Codex

В конце выведи:

## 1. Что создано

По группам:

- judge adapter;
- core;
- contracts;
- tests/scripts;
- collaboration memory;
- frontend/backend preparation;
- documentation.

## 2. Ключевые архитектурные решения

Не более 12 пунктов.

## 3. Изменённые файлы

Покажи `git status --short` и поясни назначение групп файлов.

## 4. Реально запущенные команды

Таблица:

| Команда | Статус | Краткий результат |
|---|---|---|
| ... | PASS/FAIL/NOT_RUN | ... |

## 5. Acceptance criteria

Таблица со статусами `PASS`, `FAIL`, `BLOCKED`, `NOT_APPLICABLE`.

## 6. Проверка organizer-owned файлов

Покажи, что они не изменены, либо честно перечисли случайные изменения как blocker.

## 7. Что намеренно не реализовано

Обязательно указать, что продвинутая стратегия, полноценный Frontend и полноценный Backend относятся к следующим этапам.

## 8. Инструкция следующему Frontend-агенту

Указать точный read-order и путь к `.codex/prompts/02-frontend.md`.

## 9. Рекомендуемые ручные действия человека

Включи:

```bash
git diff --check
git status --short
```

После ручного review и повторной проверки предложи commit message:

```text
chore(architecture): bootstrap sequential multi-agent project
```

Если работа логически разделяется на несколько подтверждаемых результатов, предложи несколько Conventional Commits, например:

```text
chore(architecture): define project boundaries and agent workflow
feat(core): add minimal judge-compatible strategy engine
feat(contracts): add API v1 schema and frontend fixtures
docs: add setup, handoff and collaboration guides
```

Но **не выполняй commit или push самостоятельно**.

# 19. Критические запреты

Никогда не:

- изменяй organizer-owned files;
- выдумывай успешные тесты;
- заявляй готовность Frontend/Backend до их реализации;
- делай commit/push;
- применяй force/reset/clean;
- храни ключи в коде;
- связывай judge agent с API или UI;
- требуй личный аккаунт для проверки;
- подгоняй алгоритм под mock score;
- извлекай скрытую модель среды;
- оставляй важное решение только в финальном сообщении;
- переписывай старые handoff как будто история этапов не существовала;
- начинай создавать сложную инфраструктуру, не нужную для демонстрации.

Главный критерий качества этой сессии: следующий участник с новым аккаунтом и новой Codex-сессией должен после обычного `git pull --ff-only` понять проект только по репозиторию, безопасно реализовать Frontend по fixtures и не нарушить судейский контур.
